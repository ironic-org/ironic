# Migration Guide — v1.2.x

This guide covers behavior changes introduced in the v1.2.x release line, which
applies on top of the [v1.0.x guide](/docs/migrations/v1.0.x).

---

## 1. `#[event_handler]` now auto-registers by default

**What changed (v1.2.6):**

`#[event_handler]` previously generated a registration function you had to call
yourself. It now generates an auto-registering registrar (an `impl AsyncModuleInit`
struct) that registers the handler in the DI container at startup.

**If your code compiled without explicit registration calls:**

You're done — handlers now register automatically. Remove any manual
`__event_handler_reg_*()` calls that reference the old generated struct.

**If you relied on manual registration (conditional / custom ordering):**

Add the `manual_register` attribute to opt out:

```rust
// Old (v1.0.x): registration was always manual
#[event_handler(topic = "order.created")]
async fn on_order_created(event: Arc<OrderCreatedEvent>) {
    // ...
}

// New (v1.2.x): automatic — omit manual_register for the default behavior
#[event_handler(topic = "order.created")]
async fn on_order_created(event: Arc<OrderCreatedEvent>) {
    // ...
}

// Still want manual control? Opt out explicitly:
#[event_handler(topic = "order.created", manual_register)]
async fn on_order_created_manual(event: Arc<OrderCreatedEvent>) {
    // ...
}
```

With `manual_register`, the macro still generates
`__event_handler_reg_on_order_created_manual()`, but it does **not** generate the
`__EventHandlerAuto_*` registrar struct. Call the registration function yourself.

### Migration steps

1. Upgrade to `ironic 1.2.6` (or later)
2. Build — the compiler points at any call sites referencing the old generated structs
3. Decide per handler: keep auto-register (default) or add `manual_register`
4. Delete manual registration calls for handlers you want auto-registered

## 2. Transport providers (`EventClient` / `EventServer`)

**What changed (v1.2.3–v1.2.4):**

Cross-service event I/O moved behind injectable providers:

- `EventClient` — emit events to a broker (Kafka, Redis pub/sub, or in-memory)
- `EventServer` — consume events with auto-connect/listen lifecycle

The old direct-broker usage is replaced by these providers. Configure via
`TransportConfig` / `TransportKind`:

```rust
use ironic::distributed::{TransportConfig, TransportKind};

// Old (v1.0.x): manual broker client wiring
// New (v1.2.x): configure the transport provider
let transport = TransportConfig {
    kind: TransportKind::InMemory,
    // ...
};

// Handlers can now also receive the client to emit events:
#[event_handler(transport = "order.created", auto_register)]
async fn on_order_created(event: Arc<OrderCreatedEvent>, client: Arc<EventClient>) {
    client.publish("order.fulfilled", &OrderFulfilledEvent { /* ... */ }).await;
}
```

### Migration steps

1. Configure `TransportConfig` with your broker kind (Kafka, Redis, or in-memory)
2. Replace direct producer/consumer construction with `EventClient` / `EventServer` injection
3. Use `#[event_handler(transport = "...")]` to register consumers with the server

> **See also:** the full walkthrough in [Transport events](/docs/transport/events).

## 3. Auto-validation pipe (v1.2.7)

**What changed:**

A new auto-validation pipe runs automatically — `#[routes]` inserts a
`validate_for::<T>()` pipe for every `#[body]`, `#[form]`, and `#[query]`
parameter when the `validation` feature is enabled. DTOs are validated right
after deserialization, before the handler runs — no explicit pipe needed.

```rust
#[routes]
async fn create(@body dto: CreateProductDto) -> Result<HttpStatus, HttpError> {
    // dto is already validated — no manual .validate() call needed
}

// Invalid payload → 422 Unprocessable Entity, error code VALIDATION_FAILED
```

### Migration steps

1. Upgrade to `ironic 1.2.7` (or later) with the `validation` feature enabled
2. Verify DTOs carry `garde::Validate` rules
3. Remove now-redundant explicit validation pipes if the auto pipe covers the same rules
4. Review test fixtures — invalid DTOs now fail with `422 VALIDATION_FAILED` before the handler runs
